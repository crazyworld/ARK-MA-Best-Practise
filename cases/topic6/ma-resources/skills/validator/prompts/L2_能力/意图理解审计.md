# 意图理解审计

> **层级**: L2 能力层
> **加载**: Supervisor完成意图拆解后自动触发
> **审计模式**: 全量审计（在Supervisor稳定前）

---

## 一、审计目标

```
确保Supervisor对用户意图的理解准确、完整、无遗漏
```

**核心价值**：意图理解是全链条的起点，错误会导致后续所有工作"正确地做错误的事"。

---

## 二、审计对象

### 2.1 输入数据

| 数据项 | 来源 | 说明 |
|--------|------|------|
| **用户原始输入** | Supervisor项目log | 用户的原始文字/语音输入 |
| **Supervisor理解** | Supervisor项目log | Supervisor对需求的解读 |
| **任务拆解** | Supervisor项目log | 拆解后的子任务列表 |
| **上下文** | 历史对话/项目背景 | 可能影响理解的背景信息 |

### 2.2 项目log格式要求

Supervisor需提供结构化的项目log，便于Validator审计：

```markdown
## 项目log - {项目ID}

### 用户原始输入
{完整记录用户输入}

### 意图理解
- **核心需求**: {1句话概括}
- **关键要素**: {列出关键要素}
- **隐含假设**: {明确标注假设}
- **约束条件**: {时间/范围/格式等}

### 任务拆解
1. {任务1} → {负责Agent}
2. {任务2} → {负责Agent}
...

### 确认点（如有）
- {需要与用户确认的点}
```

## 三、检查规则

### 3.1 需求完整性检查

**目标**：用户需求的关键要素是否都被识别

**检查逻辑**：
1. 提取用户输入中的关键词/实体（行业、品牌、时间、指标等）
2. 检查Supervisor理解中是否覆盖这些要素
3. 标注遗漏项

**常见遗漏**：
- 时间范围（用户说"最近"，Supervisor未明确）
- 地域范围（默认中国，但用户可能指全球）
- 输出格式（用户期望PPT，Supervisor理解为报告）

### 3.2 理解准确性检查

**目标**：Supervisor的理解是否与用户原意一致

**检查逻辑**：
1. 对比用户原始输入与Supervisor理解
2. 识别语义偏差（如"分析"被理解为"统计"）
3. 识别范围偏差（如"市场"被理解为"细分市场"）

**常见偏差**：
- 动词误解（"分析" vs "对比" vs "预测"）
- 范围扩大/缩小（"行业" vs "细分品类"）
- 主体混淆（"我们品牌" vs "竞品"）

### 3.3 假设显性化检查

**目标**：隐含假设是否被明确标注

**检查逻辑**：
1. 识别Supervisor理解中的隐含假设
2. 检查这些假设是否被明确标注
3. 标注未显性化的假设

**常见隐含假设**：
- 数据来源假设（默认使用某数据源）
- 分析框架假设（默认使用某方法论）
- 时效性假设（默认使用最新数据）

### 3.4 拆解覆盖度检查

**目标**：任务拆解是否覆盖用户需求

**检查逻辑**：
1. 将用户需求分解为子需求
2. 检查每个子需求是否有对应任务
3. 标注未覆盖的需求

**常见遗漏**：
- 用户提到的附加要求（"顺便看看..."）
- 隐含的对比需求（用户提到A，可能期望与B对比）
- 输出后的动作（用户可能期望后续推荐）

### 3.5 遗漏检测

**目标**：是否遗漏用户的隐含需求或上下文

**检查逻辑**：
1. 分析用户可能的真实目的（Why behind Why）
2. 检查是否有未表达但可能期望的内容
3. 标注潜在遗漏

**常见遗漏**：
- 用户问"A品牌怎么样"，可能隐含"是否值得投资"
- 用户问"市场规模"，可能隐含"增长趋势和预测"
- 用户问"竞品分析"，可能隐含"我们如何应对"

## 四、输出规范

### 4.1 快速反馈格式

```markdown
## 意图审计 - {项目ID}

| 检查项 | 状态 |
|--------|------|
| 需求完整性 | ✅/⚠️/❌ |
| 理解准确性 | ✅/⚠️/❌ |
| 假设显性化 | ✅/⚠️/❌ |
| 拆解覆盖度 | ✅/⚠️/❌ |
| 遗漏检测 | ✅/⚠️/❌ |

**问题**: {仅列出有问题的项，一句话}
**结论**: ✅通过 / ⚠️需确认 / ❌阻断
```

**示例**：
```
问题: 需求含"年轻化策略", 拆解中缺失; "最近"时间范围未明确
结论: ❌阻断
```

```
问题: 无
结论: ✅通过
```

### 4.2 状态判定规则

| 状态 | 判定条件 | 后续处理 |
|------|----------|----------|
| ✅ 通过 | 所有检查项均无问题 | 流程继续 |
| ⚠️ 建议确认 | 有1-2个中等问题，不影响核心理解 | 提示确认，流程可继续 |
| ❌ 需重新理解 | 有高严重度问题，或多个中等问题 | 阻断，要求重新理解 |

---

## 五、性能要求

| 指标 | 目标 | 说明 |
|------|------|------|
| **单次审计耗时** | <60秒 | 不阻塞主流程 |
| **单项检查耗时** | <10秒 | 聚焦关键，不过度审计 |
| **误报率** | <10% | 避免过度拦截 |
| **漏报率** | <5% | 关键问题必须发现 |

**快速审计原则**：
- 聚焦核心要素，不做细枝末节检查
- 有明显问题立即标注，不反复求证
- 边界case标注为⚠️，让Supervisor决定是否确认

```
问题: 遗漏"五粮液"; 遗漏"对比分析"; 遗漏"年轻化策略"
结论: ❌阻断
```
