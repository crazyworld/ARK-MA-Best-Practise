>
> 新增案例由 gateway 侧 Memory Store API 追加,Agent 不写。

## E1 · C0"是否营销可用"矫枉过正误伤正常内容

- **阶段**:Phase C(C0 基础事实层)
- **现象**:v2 修复 v1 的 5.4% "商业实体非空却选无" 违规后,新问题:误伤行业技术趋势 / 风险信号 / 统计对比类内容,判"不可用"
- **根因**:修复规则时只加了"不许漏判"的约束,没有同时约束"不许扩大判定范围",是单向修补
- **修正**:v3 同时收紧两个方向,5 条规则修复 + 机读优化瘦身,真实 DataHub HC1 验收通过(是否营销可用 53.91%,接近历史 58% 基线)
- **预防**:改标注判断规则时,检查是否只解决了"漏判"或只解决了"误判"其中一个方向,两个方向都要有真实数据验证

## E2 · C2 事件归档 07 阶段撞 max_tokens 截断,整阶段失败

- **阶段**:Phase C 第二批(C2 事件合并)
- **现象**:W35 全量测试(3517 条,四平台并发跑 C2),知乎因 `07_block_archive.py` 单批次 `max_tokens=16000` 截断失败
- **根因**:块大小按条数(60 条)固定,未考虑实际内容长度差异,大块遇到长文本记录时超限
- **修正**:本地应急补丁(max-tokens 16000→24000 + 超时对半拆分兜底);后升级到官方 v2.0.0(先原样重试一次、仍截断才对半拆分,实测输出长度是随机的,同块重跑能从 16000 token 降到 11K)
- **预防**:批处理类 LLM 调用遇到长度上限,先验证"是否重试就能过",不要直接假设需要拆分 / 减小批量——重跑成本远低于拆分逻辑复杂度

## E3 · 微博标题清洗顿号误加,69% 误改率

- **阶段**:Phase B/C(`00_clean_titles.py`,微博专属)
- **现象**:清洗规则"空格连接的两部分判不准就用顿号",159 次分隔符归一里 109 次(69%)是误改,把"主体+事项"误判成并列关系("库克 华为"→"库克、华为",实际是"库克评价华为")
- **根因**:规则默认值方向错误,"判不准"时选择了会新增信息断言(加顿号=断言并列关系)而不是保持原样
- **修正**:默认值反过来,判不准就保留原空格不加顿号;加 `NEW_SEPARATOR` 本地校验拦截,原文无顿号清洗后有一律回退
- **预防**:"清洗类" 规则的默认值原则是"不确定时不改动",不是"不确定时选一个看起来更规范的"——任何新增字符 / 新增关系断言都是在替模型下判断,风险比保持原样高

## E4 · Prompt 升版本后多处文档未同步,版本号记载矛盾

- **阶段**:跨阶段(文档维护)
- **现象**:R1/R4/R5 升级到 v2 后,`_版本状态.md`(启动必读的权威文件)仍记载 v1,跟对应 skill 的 `SKILL.md` 实际记载的 v2 矛盾,持续到打包前排查才发现
- **根因**:版本升级时只更新了 skill 自己 SKILL.md 的版本表,没有回写"镜像"文件;两处都是"记录版本号"的地方,但只有一处被当成日常更新的对象
- **修正**:以 skill 内 `SKILL.md` 「当前 Prompt 版本」段为权威源覆盖同步,并在 `_版本状态.md` 顶部加权威来源声明
- **预防**:任何"权威源 + 镜像"结构的文档,改权威源时同一次修改里必须同步镜像。本项目里 skill 内 `SKILL.md` 是权威源,memory `/{memstore_id}/topic6/_版本状态.md` 是镜像,只能由 gateway Memory Store API 同步,Agent 不写。

## E5~E17 · 客户 V2 运行期案例(MA 适配摘要)

> 来源:客户 V2 `agent/LM/错误案例库.md` E5~E17(完整排查过程见客户包原文)。
> 下面只保留对 MA 运行仍有约束力的结论；"已固化"表示规则已写进 MA 脚本，Agent 不需要也不得手工复做。

### E5 · DataHub 任务 SUCCESS 但行级内容为空
- **结论**:任务级状态只代表流程跑完，不代表结果可用。有效率 = JSON 可解析且主判断字段非空
- **MA**:已固化(`datahub_annotate.py` 空主字段计入失败行并自动补标)。Agent 只看 `valid_rate`/`status`,不得以 SUCCESS 为由跳过质量判断

### E6 · C2 缓存按位置编号撞号，跨批次静默读到旧数据
- **结论**:复用第三方缓存前必须确认缓存键是内容哈希还是位置编号
- **MA**:已固化(C2 relay 缓存键 = 代码哈希 + 整批内容哈希，并校验输出哈希)。禁止手工删改 `c2_run/` 下缓存来"强制重跑"

### E7 / E8 / E9 · Prompt 修改的评估方法
- **E7**:改 Prompt 的格式约束会反向影响前面字段的判断(LLM 整体生成),改完必须用真实数据重跑关键占比
- **E8**:给字段加触发门槛时，要检查它与其他强制规则叠加后是否堵死某个分支；按类别统计命中分布才能发现
- **E9**:同一 Prompt 同一数据两次调用占比可差 ~12pp;单次结果不足以把占比变化归因到 Prompt 改动
- **MA**:Agent 运行时不改 Prompt(R06)。HC 审核人质疑占比异常时，按 R15 报告"需 Prompt 维护方用真实数据多次对照",不得自行改写或换版本

### E10 · E4 单次长输出调用在全量规模下连续截断
- **结论**:输出随数据规模线性增长的任务要拆成职责单一的子调用，不能靠调大 max_tokens 兜底
- **MA**:已固化(`pipeline_e.py` E4 打标∥枚举→仲裁→A/B 组并发撰写)。禁止手工拆分或单独调用子 Prompt

### E13 · E2 节点日历指向错误格式文件，静默读空致「营销节点」全错
- **结论**:不要设置 `MARKETING_CALENDAR_PATH`;默认日历 `/mnt/skills/topic6-fetch-normalize/references/marketing_calendar_2026.csv` 已与客户 V2 节点集合一致(223 个)
- **MA**:已固化(日历解析出 0 个节点直接报错)。E2「上周节点」大面积出现「锚点未核实」时，先怀疑日历而不是数据

### E14 · 交付链路"设计了但没接进主流程"
- **结论**:新增的发布/推送步骤必须接进主流程对应阶段，不能依赖执行者记得手动补
- **MA**:妙搭发布已是 Phase H 必经步骤。Phase G/H 不得因"可选"而跳过

### E15 · E3 截断重试把半截旧结果和新结果拼接，平台块重复 + 错误「无营销可用」块
- **结论**:截断重试必须整体替换；自检要查块唯一性与跨版块一致性，不能只查标题存在
- **MA**:已固化(`pipeline_e.py` 截断时丢弃旧结果整体重跑；`report_self_check.py` 平台重复/矛盾空块判 fail)。自检 fail 时按既定 `--sections` 重跑，不得手工删块

### E16 · 机器侧"展开上限"预截断终稿内容
- **结论**:机器产出必须完整，精简与否由 HC3 人工决定；终稿分析列不应出现 `—` 留白(「涉及品牌」无品牌时的 `—` 属合理空)
- **MA**:已固化(舆情风险全部写完整)。Agent 不得以"篇幅过长"为由删减版块内容

### E17 · E2「上周节点回顾」被「营销可用」闸门卡掉真实节点(霜降)
- **结论**:节点客观存在但不含品牌时也应展示，由 HC3 决定去留
- **MA**:已固化(`run_stats.py` E2 用全量宽表)。HC3 看到无品牌节点属正常，不是数据错误
