### 多活动、抽样与 Validator 审核适用性规则（P0，Phase-发现 / Phase-ugc-discovery / 轮次二均适用）

**① 按活动预拆分（防止多活动标签混用）**
- 数据含多个「分析对象」时，Phase-发现、Phase-ugc-discovery 必须**逐个活动**运行，显式传入 `--campaign-filter {分析对象}`；脚本检测到多个分析对象且未指定时直接报错
- 每个活动各自产出：观点候选（正/负）、`ugc_category_list`；Validator 审核、注入 annotation_prompt、轮次二任务提交均**按活动分别进行**，不同活动的类别列表不得混用（统计聚合本就按活动分组，类别集合允许不同）
- `是否活动相关` 本就按各活动独立判定，发现阶段的样本池必须与之一致

**② 抽样**
- 默认 `mixed`：互动量 Top 50% + 其余随机 50%（固定 seed=42，可复现），避免只看高互动帖而遗漏低互动的参与方式/观点
- 样本量：观点（正/负各）默认 200（KS 区间 150–200）；UGC 参与方式默认 150（区间 100–150）；池不足则取全量
- 类别数：正面 5–8，负面 3–5，UGC 参与方式 3–6
- 输出 JSON 记录 `pool_size / sampled / sampling`；审核输入写明「基于 N/M 条样本」

**③ 适用性判定与 Validator 审核（不适用 ≠ 失败）**

| 场景 | 判定 | 脚本输出 | Validator | 轮次二处理 | 报告呈现 |
|------|------|---------|----|-----------|---------|
| `content_scope=仅PGC` | ugc 发现不适用（`pgc_only_scope`） | `status=not_applicable` | 无需确认 | `ugc_category` 全部填 N/A | 2.N.4② 保留标题，不出图，注明「本次仅分析 PGC 内容」 |
| 活动相关 UGC = 0（`no_ugc`） | ugc 发现不适用 | 同上 | 无需确认 | 同上 | 保留标题，注明「未采集到活动相关 UGC」 |
| 活动相关 UGC < 10（`too_few_ugc`） | ugc 发现不适用 | 同上 | 无需确认 | 同上 | 保留标题，注明「活动相关 UGC 仅 N 条，样本不足，暂不做参与方式分类」 |
| 某情感方向（活动相关）< 10 条（`too_few_posts`） | 该方向观点发现不适用 | 同上 | 无需确认 | 该方向不提交观点任务，`观点(AI)` 填「无」 | 2.N.3 该方向注明「{方向}内容仅 N 条，不做观点提取」 |
| 其余 | 适用 | `status=ok, hc_required=false, validator_required=true` | **需独立 Validator 审核** | 使用审核通过的列表 | 正常 |

- **Validator 规则为「适用项均通过」**：`status=ok` 的类别及来源须独立审核；不适用项记录原因，不阻塞轮次二。按 QC 协议标注审核节执行
- 阈值默认 10，脚本参数 `--min-posts`；`discussion_dimension` 不受上述影响，始终对全部活动相关行标注

**目标字段**：情感(AI) / 是否活动相关(AI)

### 标注前去噪执行约束（P0，对应 Step 1.5）

### Phase-发现：观点类别发现（两路径均执行，标注前去噪及轮次一完成后）

1. 对**每个活动**（`--campaign-filter`），从 annotated_data.xlsx 取 `是否活动相关=是` 且 `情感(AI)` 为正面/负面的内容，各取 **150-200 条**混合样本（互动 Top 50% + 随机 50%；池不足取全量；规则见「多活动、抽样与 Validator 审核适用性规则」）
2. 对正/负面样本各自调用 claude-haiku-4-5-20251001 归纳观点候选（`blueai-opinion-discovery-skill`）：
   - 正面 Prompt：归纳 5-8 个主要正面观点类别，每类附 2-3 条代表性原文，输出 JSON
   - 负面 Prompt：归纳 3-5 个主要负面观点类别，每类附 2-3 条代表性原文，输出 JSON
   - **类别定义（P0）**：观点类别 = 用户**讨论的话题/对象/方面**（口感风味、价格优惠、联名周边），名词性短语命名；**不是**情感或态度——情感已由 `情感(AI)` 判定，类别名与定义中不得出现好评/差评/吐槽/喜欢/失望/推荐等倾向词，也不写成“XX好/XX差”；倾向表述放进判断标准而非类别名
   - **MECE**：互斥（任取两类能用一句话区分）、穷尽（覆盖绝大多数内容，余者归“其他”，不单设“其他”类）、同一分类轴（都按话题，不混入人群/平台等维度）
   - 脚本对类别名自动检查，命中倾向措辞、兜底类（其他/未分类）、类别数超出要求区间，会在输出 `warnings` 中提示，审核时附上并核查（实测模型常超出数量要求并自行添加“其他”类）
   - 某方向（活动相关）内容 < 10 条 → `status=not_applicable`，该方向不做观点提取、无需人工确认
3. 将正/负观点类别、总结、真实来源帖子及定位信息交独立 Validator：对照原帖上下文核查总结是否准确；不能只审类别名称，代表帖之外也核对其他发现样本。见 QC 协议标注审核节。
4. Validator 提意见，Producer 修改后复审；适用项均通过后再注入轮次二，不适用方向沿用填“无”规则。

### Phase-ugc-discovery：UGC 参与方式自主发现（轮次一完成后，与 Phase-发现并行）

> **设计思路**：ugc_category 不使用固定标签。不同活动的用户参与模式差异很大（线下联名开店 vs 播客赞助 vs 话题挑战各不相同），LLM 读实际 UGC 内容自主归纳，比预设标签更能反映该活动的真实参与形态。

**执行步骤**：

1. 对**每个活动**（`--campaign-filter`），从 annotated_data.xlsx 中取 `是否活动相关(AI)=是` 且 `内容类型=UGC` 的行，抽取 **100-150 条**混合样本（互动 Top 50% + 随机 50%，固定 seed；数量不足取全量）；`仅PGC` / 无 UGC / UGC < 10 条 → `status=not_applicable`，直接结束（无需人工确认）
2. 调用 claude-haiku-4-5-20251001，输入抽样内容，使用以下 Prompt：

```
## 角色
你是一位用户研究分析师，擅长识别用户在营销活动中的自发参与行为模式。

## 任务
阅读以下「{campaign_name}」活动的用户生产内容（UGC）样本，
识别用户参与该活动的**主要方式**，归纳出 3-6 个行为类别。

## 要求
- 参与方式 = 用户**做了什么动作**、**采用什么内容形式**（如到店打卡、开箱测评、晒单分享、二创改编、提问求助）；类别名称简洁（2-4字），用动作或内容形式命名
- 动作（到店打卡、二创改编）与内容形式（开箱测评、晒单分享）可在同一套类别中并列，但类别间不得重叠，不得混入话题、情感或人群维度
- **不得按情感、态度或观点倾向分类**：类别名与定义中不出现好评、吐槽、避雷、种草、安利、喜欢、失望等倾向词；同样的动作和形式，无论内容夸还是骂，归入同一类
- 每个类别配一句判断标准（什么样的帖子属于这类）
- 每个类别附 2 条原始帖子内容作为示例（直接从输入内容中选取）
- **MECE**：互斥（任取两类能用一句话区分，每条帖子按主要参与方式只归一类）、穷尽（覆盖绝大多数内容，余者归“其他”，不单设“其他”类）

## 输入 UGC 样本
{sampled_ugc_posts}

## 输出格式（JSON）
{
  "categories": [
    {
      "name": "类别名称",
      "definition": "一句话判断标准",
      "examples": ["原文示例1（前80字）", "原文示例2（前80字）"]
    },
    ...
  ]
}
```

3. 脚本输出 `ugc_category_list.json`（含 `status / pool_size / sampled / sampling / categories`）；`status=not_applicable` 时本步骤到此结束，`ugc_category` 全部填 N/A
4. **独立 Validator 审核**：与 D1 共用 validate 节点，对照来源帖子核查参与方式、类别定义及 warnings；Producer 按意见修改后复审，适用项均通过后才进入步骤5，不再等待人工确认。
5. 将 `ugc_category_list` 注入 `annotation_prompt.md` 的项目配置区（`ugc_category_list` 字段）
6. 进行轮次二 ugc_category 全量标注

**输出**：`ugc_category_list`（含 3-6 个类别，每类有名称、定义、示例）→ Validator 审核通过后注入 annotation_prompt.md 项目配置区

**说明**：
- **必须经独立 Validator 审核类别及来源**，确认是否准确反映真实参与形态
- Validator 提修改意见，Producer 修复后重新提交审核
- 若发现步骤输出明显不合理（如所有帖子归入同一类），可重新运行或扩大样本量
- 类别来自样本，可能漏掉低频参与方式：轮次二后 `其他` 占比 > 20% 时，用更大/混合样本重跑本步骤并重新提交 Validator 审核（见「轮次二出口：标注覆盖检查」）
- 报告 ② UGC 参与方式节需展示本活动发现的类别名称（不再是固定4类），让读者理解分类依据

Step 3: 统计聚合（按"分析对象"字段分组，每个活动独立输出）
  - **总口径（P0）**：以下所有指标均只统计 `是否活动相关=是` 的内容；`是否活动相关=否` 的检索噪音不进入任何图表。轮次一未标注（非是/否）的行同样排除并告警。`stats_scope` 记录“监测检索原始口径 / 活动相关 / 剔除条数”
  - 声量趋势：by-day × 分析对象 × 平台 × 内容类型（"内容类型"字段，原始数据已有）
  - 互动量汇总：by 分析对象 × 平台 × 内容类型
  - 情感分布：分母 = 该活动的活动相关声量，按分析对象分组计算
  - 热门内容 Top 10：仅"是否活动相关=是"，按互动量降序（按分析对象）；由 `content_stats.py` 输出候选榜与 Top 10，Producer 按 `KS_Noise_Review.md` 审核；发现噪音自动回写统一相关性并重跑全部统计，不再单靠 `--exclude-file` 只改榜单。
  - PGC/UGC 结构（条数、占比、条均互动量）、正/负面观点 TOP5（占比、代表性原文）：同样由 `content_stats.py` 输出，不再由各项目临时计算
  - 【新增】达人层级效能：按 `kol_level` 分组，计算各层级声量占比 + 条均互动量
      - **排除范围**：`kol_level`=素人 和 `kol_level`=未知 均**不纳入达人效能图表**（素人与 UGC 定义重叠，见 KS_Metrics_Calculation.md；未知无法定级）
      - 统计范围：该分析对象内**活动相关**的 PGC 内容
      - 仅统计头部/腰部/尾部三层；条均互动量 = 该层级总互动量 ÷ 该层级帖子数（分母是帖子数，不是达人数）
  - 【新增】UGC 参与方式分布：按 `ugc_category` 统计各类别占比
      分母 = `是否活动相关`=是 且 `内容类型`=UGC 的行总数
  - 【新增】分维度 NSR：按 `discussion_dimension` 分别计算品牌 / 产品 / 活动三个维度的 NSR
      NSR = (正面数 - 负面数) / (正面数 + 负面数) × 100%
      （分母为正面+负面，不含中性，与 KS_Metrics_Calculation.md v0.6 一致）
      情感来源：`情感(AI)` 字段；范围：`是否活动相关`=是 且 `discussion_dimension`=对应维度 的行
      各维度 正面+负面合计 < 30 条（不是总行数）时标注「样本不足」，不输出 NSR 数值
  - 输出：stats_*_{活动名}.xlsx（文件名含活动名称以区分）
```

### 品牌取数关键词来源

品牌关键词、品牌过滤词以需求确认单为准（Supervisor 收集阶段已做『关键词预检』，品牌口径是否覆盖活动关键词已由用户确认，见 LM #46）。基准期必须使用与活动期完全相同的关键词和过滤词。

**活动数据过滤词核对（P0，拿到活动 Excel 后、品牌取数之前做）**：确认单的『活动取数过滤词』不一定已体现在 Excel 里，需先核对，品牌侧才能用同一套筛子。
1. 运行 `python ../../Skills/blueai-stats-aggregation-skill/scripts/check_filterwords.py --input 原始数据/{活动数据}.xlsx --filterwords "{活动过滤词，| 连接}" --output 03_数据接收及处理/filterword_check.json`（在标题、内容、话题三列按字面包含搜索，不区分大小写）
2. 退出码 0（全部 0 命中）：Excel 已按这些词清洗，品牌过滤词并入同一套词，继续后续评估与取数
3. 退出码 1（有命中）：**不动数据**，把命中的词和条数告诉用户，由用户决定这些内容保留还是排除；用户定之前不做品牌取数
4. 活动过滤词为空时无需核对
5. **多活动时的交叉核对**：品牌过滤词要合并所有活动的过滤词，而每个活动的 Excel 只按自己的过滤词清洗过。合并前，对每个活动的 Excel，用**其他活动的过滤词**再运行一次上述脚本。全部 0 命中 → 可直接合并；有命中 → 说明该活动有内容会被品牌侧多排掉，把“活动 X 的数据里有 N 条含活动 Y 的过滤词 Z”告诉用户，由用户决定该词是否仍并入品牌过滤词，定之前不做品牌取数

**过滤词误伤评估（P0，仅当需求确认单『补入品牌关键词的活动关键词』不为“无”、且『关键词预检』显示活动过滤词已并入品牌过滤词时执行，取数前做）**：过滤词对该次查询的所有关键词全局生效，并入的活动过滤词可能误排品牌本身的正常内容。
1. 用品牌**原关键词**（并入前的品牌关键词，不含补入的话题词）查询两次，平台、日期、`content_mode` 与正式取数一致：A = 不带并入的活动过滤词（只带原品牌过滤词，无则为空）；B = 带上并入后的全部过滤词
2. A−B = 原品牌内容被新增过滤词误排的条数，连同 A、B、占比记录在 `03_数据接收及处理/` 的取数记录中
3. A−B 占 A **≤ 5%**：可并入，按确认单取数
4. A−B 占 A **> 5%**：把新增过滤词用 `|` 拆成单个词，逐词与 A 对比，找出误伤词；把误伤词列给用户，由用户决定从品牌过滤词中去掉哪些，更新确认单『关键词预检』后再取数
5. 5% 为缺省阈值，用户另有要求时以用户为准
6. 活动期和基准期都要用评估后最终确定的同一套过滤词

若 `aggregate.py` 提示『品牌同期总声量 < 活动相关声量』，先回查确认单『关键词预检』，再核对平台、`content_scope`、日期窗口是否与活动 Excel 一致；核实前不得把 >100% 的声量贡献参考写入报告。
