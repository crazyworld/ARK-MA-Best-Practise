# Topic5 活动原帖获取与交接

> 版本：v0.5 · 2026-11-09
> 2026-11-09 用户明确：Topic5 调用 `ssjh-social-task` 只抓帖子，不采集或下载评论、回帖。任务创建前显式写入主帖条件，不依赖 Skill 模板默认值；帖子自身的评论数仍保留为互动指标。
> 路由明确：品牌关键词`brand_keyword`与品牌过滤词`brand_filter`交`SSJH-Social-Stat`查询；活动关键词`activity_keywords`与活动过滤词`activity_filter`交`ssjh-social-task`抓取原帖。两套条件分别使用，不互换或自动合并过滤词。
> 字段更正：用户确认 `ssjh-social-task` 获取的数据表中「内容类型」可直接得到 PGC/UGC/未知；按实际返回值沿用，不重新分类。包内模板注释与该确认不一致时，不以注释推翻实际数据语义。
> 用户决定：使用 `ssjh-social-task` 替换 Topic5 中要求用户手动提供活动数据的 HC。本文为流程接入约定，尚未完成真实取数和端到端接入验收。

## 默认入口

需求解析及方案阶段完成后，由 Producer 调用 `ssjh-social-task` 获取活动原帖，不再默认暂停等待用户上传 Excel。用户主动提供的数据仍可作为已有数据接收，不对历史项目自动补采或重采。本次决定替换的是数据提供环节；不据此删除分析方案、观点标签、UGC 类别及最终交付的现有确认。

品牌聚合数据、品牌基准期和词云继续使用 `SSJH-Social-Stat`。活动原帖走完整的获取 → 字段适配 → 清洗 → 去噪 → 相关性及情感标注 → 后续分析流程。不得用声量聚合结果代替逐帖数据。

## 调用与任务恢复

1. 执行前读取已安装的 `ssjh-social-task/SKILL.md` 及其部署、操作说明。使用需求记录中已采用的活动关键词、活动过滤词、日期、平台和内容范围，不重新要求用户编写关键词。按活动分别保存任务配置和任务标识；合并报告不代表混合不同活动的取数条件。
   - 取数配置映射：`profiler.name=campaign_name`、`profiler.keywords=activity_keywords`、`profiler.filterwords=activity_filter`；日期写入`search.start_date/end_date`，检索字段显式设置`search.keyword_fields=content,title`。这些是配置映射，关键词与过滤词分别传递，不拼成同一个检索式。
   - 品牌式及品牌过滤词用于品牌查询；活动口径用于本次原帖抓取。关键词生成阶段的有限统计试查和Step 7.3的活动词云等辅助查询不能替代正式原帖抓取，也不能证明原帖已完整交付。
2. 核对当前版本实际支持的参数。Topic5 的文本检索范围、OCR 关闭等要求必须核实接口支持并写入配置，不可仅在说明中声称已设置。`仅PGC/仅UGC` 的内容范围不得误传为主帖/评论类型。存在未支持或语义不明的必要条件时停止创建任务，记录缺口并交 Supervisor 处理。
3. 先做本地诊断及数量预检。**取消手动上传 HC 不等于授权计费采集**：遵循 Skill 的数量、预算和有效采集授权门禁；已有明确授权时复用其依据，没有授权时只请求必要的采集授权，不重新索取文件。首次执行停在预检，满足创建门禁后才能创建任务。价格、私有配置不进入业务回复或报告。
4. 同一业务请求保持原 `request_id`、run、registry 和 job；超时、未知响应、工具中断均核查并恢复原任务，不换 ID 重建。按 Skill 的最短查询间隔有界推进；没有后台承载时不承诺自动通知。
5. 配置、run 和数据存放于项目工作区，业务缓存不得写入 Skill 安装目录；registry 使用部署方统一的持久位置，不为每次调用新建登记库。保留原始 JSON、导出文件、质量报告、哈希及交付记录。
6. 安装包记录了 2026-11-02 的供应商 HTTPS 证书问题，当前连通状态需重新验证。证书失败、凭证/权限缺失、依赖缺失或预算阻断时如实记录阻塞原因，不降级 HTTP、不关闭 TLS 校验，不静默改回强制用户上传。

## 只抓帖子、不下载评论（2026-11-09 用户要求）

本规则作用于 Topic5 的 `ssjh-social-task` 原帖任务：只采集帖子正文、笔记、视频或文章，不创建评论/回帖任务，也不下载评论正文。它与 PGC/UGC 内容范围是两个独立维度，不能用 PGC/UGC 代替主帖类型。

1. 创建配置时，在每个已选平台所属配置区显式设置 `search.<区>.msg_type: 1`。配置区为 `weibo`、`weixin`、`xiaohongshu`、`short_video`、`video`、`news`、`forum`；不能沿用通用模板中的 `0`（主帖及评论/回帖）或 `2`（评论/回帖）。只对实际选择的平台生效，不因补充配置扩大取数平台。
2. 微信公众号按 Skill 平台契约只取文章，配置为 `1`，不自行增加接口未支持的微信评论开关。问答平台的 `qa.msg_type: 1` 表示问题，`2` 是回答而非评论；选择此类平台时按契约核对实际内容形态，不能把“回答”误称为评论，也不能放宽为问题和回答混采。其他平台如有枚举变更，须先核实对应版本契约，不猜参数。
3. 创建前核对保存的任务配置、规范化查询及实际任务条件均落实主帖范围；数量预检也须基于同一主帖条件。预检可比性继续按 Skill 判断，不把较宽统计结果冒充主帖精确数量。
4. 恢复已有任务先检查原任务条件。原任务包含评论/回帖、范围不明或缓存混有评论时，停止其后续下载并记录范围不符；不修改原任务状态/查询，不自动新建计费任务。不得先混采下载再删评论，或通过导出模板隐藏评论冒充符合本要求。
5. 下载后按已核实的记录类型和来源语义检查范围。类型标记不明时记录异常，不猜测枚举。评论/回帖不得进入 Topic5 适配工作簿、送标集及统计分母；PGC/UGC仍沿用原列。`评论数`保留，它是帖子级互动计数，不是评论正文。
6. `acquisition_handoff.json` 记录本次 `posts_only: true`、各已选配置区的 `msg_type`、原任务范围核对、下载后范围核验结果及异常；未核验通过不得标记 `ready`。

例如同时选择微博和小红书时，任务配置中显式写入（其他条件沿用本次需求）：

```yaml
search:
  source: "weibo,xiaohongshu"
  weibo:
    msg_type: 1
  xiaohongshu:
    msg_type: 1
```

本节约束调用配置与交接审核，不修改共享 Skill 的通用默认值，不代表已经发起或验证真实取数。

## 字段适配门禁

下载成功不等于 Topic5 已可使用。原始导出原样保留，另生成适配后的工作簿及 `acquisition_handoff.json`，校验通过后才交 Step 5。适配规则以 Skill 数据字典的实际语义和本项目字段规范为准。

### 抓取后字段保留清单（2026-11-05 用户确认）

原始导出完整留存；在字段映射、全文还原及质量核验后，适配工作簿只保留以下19列，列名及顺序固定：

```text
id
分析对象
站点名称
标题
内容
视频封面内容识别
音频内容识别
视频文本识别
内容类型
话题
作者
url
发表时间
总互动量
转发数
评论数
点赞数
收藏数
粉丝数
```

- 裁剪只删除列，不删除行；以适配后的目标列名执行，不能在映射前丢弃来源字段。
- 清单外列不进入适配工作簿，包括供应商的`数据类型`、`情感`和预存的派生/AI标注列。供应商元信息与原始情感仍可在原始产物及交接记录中追溯。
- 清单内缺列须显式记录到`missing_fields`，工作簿补为空列以保持19列结构；不得补零或伪造文本。`分析对象`按已确认活动任务绑定；影响后续分析的缺口仍按现有门禁处理，补空列不代表已通过。
- `id`按文本保存；`话题`、`url`、封面/音频/视频文本识别及正文保留可用原值，全文还原和缺失指标规则继续适用。
- 裁剪后Step 5从`站点名称`的已核实映射派生`平台标签`，不再依赖`数据类型`；无法确定的平台记录异常，不默认归抖音。再追加`kol_level`，Step 6追加AI标注字段。19列限制只适用于适配输入，不重复裁剪清洗、去噪、标注输出。
- `acquisition_handoff.json`记录`retained_fields`（以上顺序）、`dropped_fields`、`missing_fields`和裁剪前后行列数；确认裁剪前后行数一致、输出列名及顺序与清单完全一致。

### 来源字段映射

| Skill 默认导出列 | Topic5 目标列 | 接入要求 |
|---|---|---|
| 内容ID | id | 按文本保存，核验唯一性；去重须结合平台和实际 ID 命名空间核实 |
| 发布时间 | 发表时间 | 核验时区、解析及活动窗口 |
| 正文 | 内容 | 保留全文；有 text_overflow 时按 Skill 的分片还原及哈希校验规则恢复，禁止把截断文本直接用于标注 |
| 作者昵称 | 作者 | 保留缺失，不编造作者 |
| 平台 | 站点名称 | 使用已核实的平台映射；原始数据类型可作为适配核验依据，但不进入19列工作簿；平台标签在Step 5从站点名称派生，未覆盖的平台须补映射后再执行 |
| 互动量 | 总互动量 | 核对平台指标口径，缺失不补零、不猜测跨平台等价关系 |
| 分析对象 | 分析对象 | 按本次活动任务绑定 campaign_name，不直接使用供应商 profiler 作为活动归属证据 |
| 内容类型 | 内容类型 | 用户确认此列可直接得到 PGC/UGC/未知；原值沿用，仅校验取值，不改名、不重新推断分类 |
| 视频封面/音频/视频文本识别（如有） | 视频封面内容识别、音频内容识别、视频文本识别 | 先核对字段语义，保留可用文本；缺失按现有规范记录，不伪造识别结果 |

Topic5 的 PGC/UGC 分类直接来自取数表的 `内容类型` 列，无需另找独立来源或新增分类步骤。保留 `PGC`、`UGC`、`未知`，其中 `未知` 单独计数，不并入 PGC/UGC。空值与非法值另行记录，不静默混同为供应商返回的 `未知`，按现有异常处理规范处理。只有实际文件缺列或返回不符合此约定时才记为字段异常；不得仅因包内模板注释写了主帖/回帖/评论就判定分类缺失，也不得用认证类型、粉丝量覆盖已有分类。

`acquisition_handoff.json` 至少记录：活动名称、条件摘要、数据来源、授权引用、request/run/job 引用、预检关系与估计依据、批准上限、实际下载及唯一记录数、原始产物与质量报告路径、文件哈希、字段映射、缺失字段、适配状态及阻塞原因。不得写入凭证、实际价表或私有费用台账。

只有下载完整性、唯一性、质量及字段语义检查通过且不存在影响后续分析的未解决缺口时，适配状态才可记为 `ready`。失败时保留原任务和已有产物；不得把部分数据声明为全量，不自动重建付费任务。

## 与后续流程衔接

获取及适配位于 Producer Step 2 后、Step 4/5 前，记为 Step 2.5，保留现有步骤编号。适配产物位于 `03_数据接收及处理/原始数据/`，交接记录与 run 路径一并提供。再执行原有活动过滤词核对、品牌聚合获取和清洗。自动取数以任务条件及交接记录核对过滤词是否落实；历史用户文件仍按现有规则针对性核实其排除状态。

Step 5.5 仍在清洗后、相关性/情感标注前去噪，明确噪音直接剔除，不新增去噪确认。活动情感继续使用 `情感(AI)`；供应商原始 `情感` 仅作来源留存，不替代 AI 标注。
